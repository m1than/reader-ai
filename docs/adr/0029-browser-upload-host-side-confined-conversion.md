> Amendment (owner, 2026-11-24), from the upload code review: the inbox quota is checked after the body is received and after the duplicate check (a re-upload of an open file is answered with its view even when the quota is full), not before the body with Content-Length. The cap of 200 MiB is still enforced before and while streaming, and only one body streams at a time under the upload lock, so the transient overshoot is at most one 200 MiB temporary file above the 1 GiB of stored open uploads.

> Amendment (owner, 2026-11-23), from SRV-INGEST revision 2 review rounds 4–6 and spikes/ingest-sysctl:
> - **The inode channel is open under every profile tried.** `fsgetpath()` on a directory's inode returns its path, and `chdir` into a known path is allowed. Neither is stopped by denying `file-read-metadata` below the work root (measured, 2026-11-23); the mechanism is not identified. A confined child that scans the inode numbers near its own work directory finds a sibling run's (measured: a ±2,000 scan).
> - **Decision 3's edits close the process channels only:** another process's arguments and environment (`kern.procargs2`, `kern.procargs`), its entry in the process table (`kern.proc.pid`, `kern.proc.all`), its cwd and executable path (`proc_pidinfo`, `proc_pidpath`) and the process list (`proc_listallpids`). They do not close the inode channel.
> - **The control is one converter run on the host at a time.** Every converter run, the CLI's (`reader-ingest <material>`) and the watcher's alike, holds `<data_dir>/ingest/locks/convert.lock` from just before its run until its cleanup has ended; an idle watcher waits without it. So no run exists alongside another for a child to join. The CLI answers `busy` (exit 3) while an upload converts, and an upload queued during a CLI run waits, shown as `queued` with "a command-line conversion is running". Whoever takes the lock next kills each leftover run's verified child and removes its work directory.
> - **Residual: cross-run denial of service.** A child that escaped an earlier run (it called `setsid()`, left its work directory and rewrote its arguments, so it was neither counted nor killed) survives, still confined: no network, no sockets, no information about other processes, no writes outside a deleted directory. It can find each later run's work directory, join that run's accounting and push it over its 8 GiB memory limit, failing every later conversion until the Mac restarts (whether logging out also ends it is not measured). There is no reliable signal, because the same argument rewrite hides it from the stray count; the symptom is repeated `memory_limit` failures on files that converted before, and the Import page names it with the remedy: restart your Mac. A `sandbox_check(pid)` spike may later give a signal.
> - **Sentences this amendment replaces:**
>   - Decision 2, "Convert": "For non-malicious runs, work directories are random and unique, so a concurrent run (another upload, or a CLI `reader-ingest`) is never counted or killed." and "An exploited child cannot learn another run's work directory through any channel tried (Decision 3); if a path leaked otherwise, it could join that run and push it over its memory limit, a denial of service of one conversion." are replaced by the control and the residual above: with one run at a time there is no concurrent run to count or kill, and the inode channel lets an escaped child find later runs.
>   - Threat row 1 (Malicious PDF): "no information about other processes (their arguments, environment, cwd and paths: the inbound channel Decision 3 closes)" now means other *processes'* paths only (their executable and cwd); directory paths remain learnable through the inode channel.
>   - Threat row 3 (Escape from the session): "Decision 3 keeps a child from learning another run's WORK; the [host] test replays the round-3 attack and requires that its child is not a member of the other run" is replaced by: Decision 3 keeps a child from learning about other processes; one converter run at a time (`convert.lock`) leaves no concurrent run to join; the [host] test replays the round-3 attack, requires that every process channel is refused, and records `fsgetpath` as open.
>   - Threat row 3, Residual: "If another run's WORK path leaked by a channel not tried, the child could join that run (measured: `chdir` into a known WORK is allowed) and push it over `memory_limit`, a denial of service of one conversion." is replaced by the residual above (the channel is measured, and the cost is every later conversion).
> - **Throughput gate met** under the amended profile: the full pilot converted 935 of 935 pages in 961.6 s (58.3 pages/min against the 10 pages/min gate), converter peak RSS 3,590.8 MiB (spikes/ingest-sysctl/results/fullrun-v2.json, 2026-11-23).

> Amends [ADR-0027](0027-native-ingest-transport-no-listener.md): its Consequences say "Ingestion of the slice is started on the Mac (`reader-ingest bashir-2025`). Browser upload waits for a later decision, which this ADR's `revisit_when` names." This is that decision. ADR-0027's Decision (no listener, the confined child, artifact over `docker exec` stdin into the worker) is unchanged except for **two profile edits** (Decision 3): the sysctl reads are narrowed to an allow-list and process-info is limited to the process itself, because the product profile let a confined child read another process's arguments and cwd (measured, spikes/ingest-sysctl). The amendment note on ADR-0027 is the owner's edit when this ADR is accepted. Its proposed text is in [0027-amendment-note.txt](0027-amendment-note.txt): the two profile edits; `receive` now also accepts an uploaded material, only under a live claim whose sha256 equals the artifact's; and ADR-0027's "No new capability" restated (the confined child gains nothing and loses the cross-process reads; the host watcher, not the child, gains the long poll and fetch over `docker exec`).

## Context

**Owner request (2026-11-23):** a first step in which the learner imports a source in the browser, then says how long they want to study it. Decision 2 of that request: "upload in the browser. An 'Import source' page: drag-and-drop PDF → progress (conversion, indexing) → the study-time question → the course plan. The host-side sandboxed converter must stay isolated. The server queues the file, and the host-side converter picks it up."

**Owner answers to this ADR's open questions (2026-11-23):** the upload cap is 200 MiB; `reader up` starts the ingest watcher by default.

**Facts that constrain the design:**
- **The converter is native and confined** (ADR-0021, accepted: Docker missed the 51 s per formula bound, 266–284 s measured). ADR-0027 (accepted) runs it as a child of a host command under a deny-default `sandbox-exec` profile: no network, no Unix sockets, no mach services, reads only its runtime, the models and its work directory, writes only that directory. Measured: 15.69–15.85 pages/min on the 20-page sample (spikes/ingest-confine), 65.5 pages/min on the full pilot with a child peak RSS of 4,025 MiB (SRV-INGEST NFR-INGEST-1).
- **Nothing on the host listens for the stack.** The worker is only on `internal: true` networks (OPS-DEPLOY), so it has no route to the host. ADR-0027 rejected a loopback listener (B), a host bind mount (C, against OPS-DEPLOY FR-DEPLOY-5) and a host command calling the api (D, a new long-lived api credential).
- **The api already mounts `blobs`** (deploy/compose.yaml, OPS-DEPLOY FR-DEPLOY-5: `blobs` on api and worker), so an upload can land on the same volume the worker reads, with no new mount.
- **The owner's Docker socket is the existing trust channel.** `reader` delivers secrets over `docker exec` stdin (ADR-0026), and `reader-ingest` sends artifacts the same way (ADR-0027).
- **The OPS-CLI watcher holds resolved secret values in memory for its lifetime** (OPS-CLI FR-CLI-8 step 4), and its spawn passes a secret bundle on fd 3.
- **sandbox-exec confines what a process may touch, not what it may consume,** and a confined process may still call `setsid()`, leaving the session its parent kills (measured by the round-1 reviewer, 2026-11-23).
- **The product profile leaks other processes' arguments and cwd** (measured by the round-3 reviewer, reproduced in spikes/ingest-sysctl, macOS 27.2): under `(allow sysctl-read)` and with no process-info rule, a confined child read a concurrent run's argv (`kern.procargs2`), cwd (`proc_pidinfo`) and executable path, learned its work directory, and made its own setsid'd child a member of that run. A sysctl deny by name did not stop `kern.procargs2`; the allow-list plus `(deny process-info*) (allow process-info* (target self))` refused every channel tried, and the converter's [host] and [local] tests (20 pilot pages included) pass under it.
- **The pilot PDF is 20,922,693 bytes for 935 pages** (verified 2026-11-20 against plan.yaml's sha256).
- **ADR-0014** keeps code derived from uploaded material out of anything that holds secrets; ADR-0012 fixes v1 to the owner's single Mac with passkey sessions, served on `localhost`; ADR-0021 Options O1/O2 call parsing untrusted documents outside a container the cost of the native path.

## Options

### Upload

There is one sensible shape, so this part has no competing options: the owner's browser sends the PDF to the api through Caddy with the owner's session, and the api stores it without parsing it. The details are the Decision's.

### Host pickup: how the host learns of an upload and gets its bytes

| Option | Gives | Costs |
| --- | --- | --- |
| **P1. A dedicated host process `reader-ingest --watch` long-polls the worker over `docker exec`; it claims an upload, fetches its bytes on the exec's stdout, and sends the artifact back on the existing receive's stdin** | No listener, no new credential, no new mount; the same channel ADR-0027 already uses in the other direction. The process holds no secret. Every byte the host takes in is bounded and checked against the claim | One more long-lived host process (started by `reader up`, OPS-CLI proposed FR-CLI-22). A `docker exec` per poll (one per 25 s when idle) and per heartbeat (one per 30 s while a claim is held), each a short Python process inside the worker's memory limit |
| P2. The OPS-CLI secret watcher also does the pickup | No new process | That process holds every resolved secret in memory (OPS-CLI FR-CLI-8). Running and supervising a converter of untrusted input from it widens the blast radius of a bug in the supervision code from "a converter child" to "a process with all secrets"; its lifecycle (restart on `reader up`, never re-resolving) also does not fit a 4 h conversion |
| P3. The host polls the api over HTTPS (`https://localhost/api/…`) | Uses the front door | The same objection as ADR-0027's D: a script cannot hold a passkey session, so it needs a new long-lived api credential, which any process of the owner's user could read and use against the edge-facing service |
| P4. A host directory mounted into the api as the inbox | The host reads files with no exec | A bind mount, which OPS-DEPLOY FR-DEPLOY-5 forbids. The host would read files that the browser-facing service wrote, through a path that service controls (symlinks, FIFOs, renames under the reader), with no transfer boundary; and the host directory becomes writable from inside a container |
| P5. `docker cp` from the worker's inbox path | No in-container command | The host parses a daemon-made tar of a path the container controls; there is no claim, lease or cancel, so two host runs could convert the same file, and progress still needs P1's channel |

### Who drives the queue

| Option | Gives | Costs |
| --- | --- | --- |
| **Q1. An `uploads` table with an explicit state machine and a lease, driven by the host's exec calls and expired by the stack's own reads; the import and indexing after it stay SRV-EVENTS jobs (`ingest.import`, `search.embed`), and the import key is authoritative once it exists** | The conversion is not a worker job (it runs on the host), so its states are honest: queued, claimed, converting, sending, then the existing jobs. A lease recovers a host that died | One table and its transitions |
| Q2. Model the conversion as an SRV-EVENTS job | Reuses retries | A job is run by the worker; the worker would have to wait for an external process, holding a job slot and its timeout for up to 4 h, and procrastinate's heartbeat semantics do not cover a host that vanishes |

## Decision

**P1 with Q1.** In order:

1. **Upload** (api, SRV-INGEST FR-INGEST-18):
   - **Route.** `POST /api/materials/uploads?language=<ru|en|other>` with the raw PDF as the body and `Content-Type: application/pdf`. Owner role only. The filename travels in the header `X-Reader-Filename` (percent-encoded UTF-8), never in the URL, so no access log or proxy log can hold it; it is display metadata only (NFC; controls, separators and bidi controls removed; at most 200 characters), never a path, never logged. SRV-AUTH FR-AUTH-12's Origin check applies unchanged; its JSON-only rule gets an exact one-entry allow-list for this route (SRV-AUTH proposed FR-AUTH-22). No multipart: the api runs no multipart parser on untrusted input.
   - **Size.** Caddy refuses a body over 200 MiB on this exact path (`request_body { max_size 200MiB }`, OPS-DEPLOY proposed FR-DEPLOY-13; owner 2026-11-23). The api enforces the same cap (209,715,200 bytes) while streaming 1 MiB chunks to a temporary file under `<BLOBS_DIR>/inbox/.tmp-<random>`, hashing as it writes, and never holds the body in memory. The whole body must arrive within 300 s (408); this numeric timeout lives in the api, not in Caddy, whose read timeouts are server-wide and would also bound the WebSocket kernel relays. 200 MiB is about 10× the pilot; the converted artifact stays under the existing 80 MiB cap independently of the PDF's size, because it holds text, not images.
   - **Magic check.** The first 8 bytes must be `%PDF-1.[0-7]` or `%PDF-2.0` at offset 0, and the last 1,024 bytes (the whole body if shorter) must contain `%%EOF` (ISO 32000-2 7.5.2 and 7.5.5). This is the only inspection the stack does: **no service in the stack parses, renders or previews the PDF.** The browser does not preview it either.
   - **One upload at a time** for the instance (a Postgres advisory lock; 409 `upload_busy`). Under that lock, before anything else, the api **sweeps crash leftovers**: every `.tmp-*` file (its writer would hold the lock) and every `<sha>.pdf` without an `uploads` row.
   - **Quota, exact.** Open uploads are those not yet handed to the import (queued, claimed, converting, sending, failed). At most 5 of them, and their bytes plus the incoming body at most 1 GiB, checked before the body (with Content-Length) and again while streaming, so there is no overshoot. Files of uploads handed to the import are the owner's retained originals and sit outside the quota; their total is reported. The remedy shown for `inbox_full` is to Discard failed uploads, cancel queued ones or wait.
   - **Dedupe by sha256.** An existing upload or declared material with that sha256 is returned instead of a second copy. A cancelled or discarded upload leaves no row, so the same bytes can be uploaded again.
   - **Storage.** `fsync`, then rename to `<BLOBS_DIR>/inbox/<sha256>.pdf`, mode 0440. The path comes only from the server-computed sha256. The blobs volume holds data only: nothing in the stack executes or imports from it.

2. **Host pickup** (`reader-ingest --watch`, SRV-INGEST FR-INGEST-20/-21; started by default by `reader up`, owner 2026-11-23, with an allow-listed environment, no inherited file descriptors, its own session and no terminal, OPS-CLI proposed FR-CLI-22; also runnable in a terminal):
   - **Stale cleanup.** At start, under its own lock, the watcher kills (after FR-INGEST-16's pid, start-time and cwd checks) and removes the runs a previous watcher left.
   - **Wait and claim.** `docker exec -i <worker> python -I -m reader.ingest.inbox next --wait 25 …` records the host heartbeat, waits on Postgres `LISTEN` for at most 25 s and atomically claims the oldest `queued` upload: a fresh random claim token and a lease of 120 s.
   - **Heartbeat.** From the claim until receive's reply, a timer runs `inbox progress --phase …` every 30 s, through fetch, model load, conversion, sending and receive; each call renews the lease and the host's `seen_at`. The lease therefore never depends on the converter producing output; four missed beats expire it. A heartbeat that arrives after its lease has passed never renews it, even if nothing else has applied the expiry yet: it applies the expiry itself and gets the cancel shape (renew or cancel, never resurrect). `--phase sending` moves `claimed` or `converting` to `sending`.
   - **The Mac stays awake** while the watcher holds a claim: it runs `caffeinate -i -w <watcher pid>` from the claim to its end. Residual: closing the lid or a forced sleep still suspends the Mac; on wake the lease has usually expired, the next heartbeat gets the cancel shape, and the upload is converted again (`attempts + 1`).
   - **Framing, bounded.** Every in-container command answers with exactly one of three shapes: success (exit 0, one JSON line of at most 4,096 bytes, or for `fetch` exactly the upload's size in bytes), **one cancel shape** (exit 3, `{"cancel":true}`, for a deleted upload, a stale claim or an upload already handed to the import), or an error (exit 1). The host reads at most 4,097 bytes of a reply and `size` + 1 bytes of a fetch, killing the exec at the bound; it drains stderr into a byte counter and never forwards it; it checks the exit code before using any byte; every exec has a host-side timeout above the command's own deadline (fetch 330 s against 300 s).
   - **Confused deputy.** The host converts only if `fetch` exited 0, its length equals the claim's `size`, its sha256 equals the claim's and the magic check passes again. In watch mode the host never opens a host path given by the stack, and every argument it puts into an exec argv is validated against a fixed pattern and passed as a list, never through a shell.
   - **Convert.** ADR-0027's child and environment under the amended profile (Decision 3; SRV-INGEST FR-INGEST-4..10), plus host-side watchdogs (FR-INGEST-22) that the sandbox cannot provide: every 2 s (a chosen tick) the watcher sums the resident memory of **this run's** processes — those whose session id (`getsid`) is the child's, plus any process whose kernel executable path is the converter's Python, started after the child, whose cwd lies under this run's work directory or whose args contain that directory's realpath, which catches a descendant that called `setsid()` — and kills them all, each re-verified just before its signal, above 8 GiB (the pilot's measured 4,025 MiB peak × 2) or when the work directory exceeds 2 GiB. For non-malicious runs, work directories are random and unique, so a concurrent run (another upload, or a CLI `reader-ingest`) is never counted or killed. An exploited child cannot learn another run's work directory through any channel tried (Decision 3); if a path leaked otherwise, it could join that run and push it over its memory limit, a denial of service of one conversion. The 4 h wall clock stays.
   - **Strays, a warning.** After every run the watcher counts detached processes (parent pid 1) whose `ps -o comm=` is the converter venv's `<VENV>/bin/python` (measured on macOS 27.2: `comm` shows that unresolved exec path) and that belong to no live run. It never kills them and keeps claiming; the count reaches the Import page as a warning. Other Python 3.14 processes on the Mac, which share the uv CPython but run from other paths, are not counted. A child that rewrites its args, or re-execs the base interpreter, changes its `comm` and is not counted.
   - **Return.** The artifact goes over the existing `reader.ingest.receive` stdin (ADR-0027), which gains the upload id and claim. Because the enqueue commits on its own, receive runs in a fixed order, each step idempotent: claim check (or the import key already exists), store, enqueue `ingest.import`, then mark the row `received`. A crash between enqueue and mark is repaired by the key-authority rule (item 5).

3. **Confinement: ADR-0027's profile with two edits** (SRV-INGEST proposed amendment of FR-INGEST-4 and INV-INGEST-4; measured in spikes/ingest-sysctl):
   - `(allow sysctl-read)` becomes an allow-list of hardware, VM and OS-identity names, with nothing under `kern.proc` or `kern.procargs`;
   - `(deny process-info*)` and `(allow process-info* (target self))`.
   Together they refuse `kern.procargs2`, `kern.procargs`, `kern.proc.pid`, `kern.proc.all`, `proc_pidinfo`, `proc_pidpath` and `proc_listallpids` against another process; either alone does not. **Open, found after review round 4 (measured 2026-11-23, spikes/ingest-sysctl):** `fsgetpath()` on another run's WORK inode still returns its path under these edits, because it needs only `file-read-metadata`, which the profile allows everywhere; an attacker can try inode numbers near its own WORK's. Listing `/.vol/<dev>/<ino>` of the shared parent and opening another WORK through `/.vol` are refused. A third edit, a metadata wall below the directory holding all WORKs (`(deny file-read-metadata (subpath WORKROOT))`, with WORKROOT itself and the child's own WORK allowed), is being measured; the product profile does not change until the cross-process probes, the inode probes included, are all refused (SRV-INGEST INV-INGEST-4). The child environment, realpath'd parameters and untrusted-WORK handling are unchanged. The edits do not change the converter's output, so `CONVERTER_VERSION` stays; the profile is read from the checkout at every run.

4. **Progress back to the UI.** The upload's displayed state is derived, never guessed:
   - from the `uploads` row: `queued` → `claimed` → `converting` (with `pages_done`/`pages_total` from the converter's validated progress lines) → `sending` → `received`;
   - then from the jobs: `importing` while `ingest.import` is queued or running, `indexing` while `search.embed` is, `ready` when both succeeded;
   - `failed` with a code. A cancelled or discarded upload has no row.
   The browser polls `GET /api/materials/uploads/{id}` (every 2 s while not terminal). Server-sent events are deferred with the rest of the outbox events.

5. **Failure, retry and cancel.**
   - **Host lost.** A lease that has passed returns the upload to `queued` with `attempts + 1`; after 3 attempts it is `failed` with `host_lost`. **The stack applies expiry itself** on every `next` and on every api read of an upload or of the list, so a dead host is noticed even when no watcher runs.
   - **The import key is authoritative.** Before any transition away from `claimed`, `converting`, `sending` or `failed` (expiry, `fail`, a new claim, Retry, Discard, cancel), the same transaction checks whether the upload's `ingest.import` key exists; if it does, the row becomes `received` and the transition is refused. Discard and cancel are therefore impossible once the import has been enqueued.
   - **Deterministic failures** (`not_pdf` after fetch, `fetch_mismatch`, `inbox_missing`, `bad_reply`, `convert_failed`, `memory_limit`, `work_limit`, `timeout`, a receive rejection) end the upload `failed` with that code and are **not** retried automatically: retrying a malicious or broken file only spends CPU. The owner's **Retry** returns a `failed` upload to `queued` with `attempts = 0` (reconvert).
   - **Import and indexing failures** are SRV-EVENTS `dead` keys. The UI shows `failed` with the job's code, and the owner's **Retry** on such an upload calls `requeue_dead` for the dead `ingest.import` or `search.embed` key, with no reconversion: the artifact is already stored. Discard stays refused there (the import key exists). The CLI's `--requeue` and `ensure` keep working.
   - **Cancel** (queued, claimed, converting) and **Discard** (failed) **delete the row and then unlink the inbox file, both under the instance's upload lock**, so a concurrent upload of the same bytes cannot rename a new file into that path in between; a crash after the commit leaves an orphan file that the next upload's sweep removes. The host's next heartbeat, `fetch` or receive gets the cancel shape, kills the run's processes and removes its work directory.
   - **Retention.** The inbox file of a received upload is kept: it is the owner's original for the deferred re-ingest and export (roadmap SRV-EXPORT, "own uploads"), outside the quota.

6. **When the host isn't running the watcher.** Nothing times out except leases: an upload waits as `queued`, and the stack never tries to reach the host. The api reports the watcher as `offline` once its last heartbeat is 60 s old, otherwise as the host reported itself: `online` or `setup_missing`, with the stray count as a separate warning (item 2) that never stops claims. The Import page shows the state and the one command that fixes it (`reader up`, or `reader-ingest --setup`). The CLI path (`reader-ingest <material id>` for reader.yaml materials) stays as it is, so the pilot keeps working without the watcher.

## Threat model

| Threat | Where it could act | Control | Residual |
| --- | --- | --- | --- |
| **Malicious PDF** (an exploit in pdfium, Docling or torch) | Only in the converter child: the stack never parses the file, and the browser never renders it | ADR-0027's deny-default profile with Decision 3's edits: no network, sockets or mach services, no exec beyond its Python, reads only its runtime, models and WORK, writes only WORK, no secrets in its environment, and no information about other processes (their arguments, environment, cwd and paths: the inbound channel Decision 3 closes). The parent treats WORK as untrusted (FR-INGEST-10) and validates the artifact twice (host, then receive) | The child's one outbound channel is the artifact's text, which enters the stack's database and, through compile and the tutor, model prompts: a malicious PDF can carry prompt injection there (handled by SRV-PIPELINE's source delimiting, VEC-PIPELINE-5), not code |
| **Decompression bomb** (Flate streams, huge page trees, object streams) | Converter child memory and disk | The 8 GiB memory and 2 GiB work-directory watchdogs over the run's processes; the 4 h wall clock; the existing artifact caps (80 MiB tar, 500,000 spans, 5,000 pages). sandbox-exec limits no resources, so the watchdogs are the control, not the profile | macOS RSS undercounts compressed and swapped memory (a hypothesis with a [local] check, below) |
| **Escape from the session** (`setsid()` in an exploited child) | Host CPU and memory, and other runs | Membership bound to this run: same session id, or the converter's kernel executable path plus a start after the child plus cwd under this run's WORK or this WORK in its args; members re-verified before each kill (FR-INGEST-22). Decision 3 keeps a child from learning another run's WORK; the [host] test replays the round-3 attack and requires that its child is not a member of the other run | A child that calls `setsid()`, moves its cwd out of WORK and rewrites its args escapes accounting and killing. It stays under the profile, which a process cannot leave: no network, no sockets, no information about other processes, writes only into a WORK that is deleted. It can hold CPU and memory until it is killed. If another run's WORK path leaked by a channel not tried, the child could join that run (measured: `chdir` into a known WORK is allowed) and push it over `memory_limit`, a denial of service of one conversion. Strays (`comm` = `<VENV>/bin/python`, measured on macOS 27.2) are a warning, never killed; an args rewrite or a re-exec of `<PYROOT>/bin/python3.14` hides a process from that count. Between a member's re-verification and its SIGKILL, pid reuse is not excluded; an owner's Python 3.14 process started inside WORK would be counted |
| **Upload DoS** (huge, slow or many bodies) | api, Caddy, blobs volume | Owner-only route; Caddy's 200 MiB `max_size`; the streamed cap with no buffering; the 300 s body deadline; one upload in flight; the exact open-upload quota (5, 1 GiB) | Retained originals grow with every import, outside the quota (deleting materials is deferred) |
| **Path traversal** | api storage, host work directory, exec argv | The inbox name is the server-computed sha256; the filename is never a path; the host validates the sha256 (`^[0-9a-f]{64}$`), the upload id (UUID) and the claim (`^[0-9a-f]{32}$`) before building argv; the host's work name stays random (FR-INGEST-1) | — |
| **Confused deputy** (the host made to convert something the server did not queue, or a file of the owner's Mac) | Host watcher | The host converts only bytes it fetched for its own live claim; in watch mode it never opens a path from the stack. Receive accepts uploaded materials only under a live claim with a matching sha256. **The sha256 check detects corruption and mix-ups only:** the stack chooses both the sha256 and the bytes, so it is not a defence against a compromised stack, which can queue any bytes it likes | A compromised api or worker can make the host convert arbitrary bytes, one at a time, without limit: there is no host-side rate limit (deferred). Each conversion is a malicious-PDF case under the profile |
| **A compromised api or worker** feeding the host bytes or lines | Host watcher | Bytes are the malicious-PDF case. ## Rejected options — why

- **P2:** the pickup would run in the process that holds every resolved secret, for up to 4 h per conversion. P1 needs no secret.
- **P3:** a new long-lived api credential for a script, the reason ADR-0027 rejected its D.
- **P4:** a bind mount (OPS-DEPLOY FR-DEPLOY-5), and the host would read through a path a browser-facing container controls.
- **P5:** no claim or cancel, and a daemon-made tar of a container-controlled path to parse on the host.
- **Q2:** a worker job slot held for up to 4 h waiting on a process the worker cannot see.

## Consequences

- **SRV-INGEST** (revision 2, proposed) owns the upload route, the `uploads` table, the `inbox` commands (`next`, `fetch`, `progress`, `fail`), receive's claim check and order, `reader-ingest --watch`, and the watchdogs.
- **Paired changes**, each drafted as proposed items in its own spec: SRV-AUTH FR-AUTH-22 (the raw-body allow-list), OPS-DEPLOY FR-DEPLOY-13 (Caddy's `max_size 200MiB` on the upload path; why the timeout lives in the api), OPS-CLI FR-CLI-22 (the watcher spawn; status; stop on `reader down`), SRV-SEARCH FR-SEARCH-10 (an uploaded material's `fts_config` from its upload's language). Drafted at promotion: SRV-CONFIG (the `up-` id prefix reserved for uploads).
- **The planner and the Import page** (SRV-PLAN, WEB-IMPORT) build on the upload's `ready` state.
- **Easier:** importing any PDF without editing reader.yaml or opening a terminal, once `reader up` runs.
- **Harder:** one more long-lived host process to supervise; the owner's Mac must be on, with the stack up, for a conversion to progress.
- **Forbidden:** any parser of the uploaded file inside the stack; any host listener; a host pickup that opens a path the stack names.

## Hypotheses (unmeasured), each with its check

- **Memory watchdog:** 8 GiB is twice one measured peak (4,025 MiB on the pilot). macOS's `ps -o rss=` reports resident pages and undercounts compressed and swapped memory. [local] a child under the product profile that allocates and touches 9 GiB is killed with `memory_limit`; a full pilot run under the watcher records the peak again.
- **Fetch throughput:** a 200 MiB fetch over `docker exec` stdout must finish within the command's 300 s deadline, i.e. at least 0.67 MiB/s through Docker Desktop's exec stream. Unmeasured; the [live] exact-cap case (SRV-INGEST FR-INGEST-18) fetches 209,715,200 bytes and records the time. If it exceeds 300 s, `revisit_when` applies.
- **Worker memory under polling:** each `next`, heartbeat and `fetch` starts a Python process inside the worker container (mem_limit 2g, OPS-DEPLOY), at most three at once (a long-poll, a heartbeat, a fetch or receive). Their size is unmeasured; the [live] run records the worker's peak `memory.peak` while a conversion is under way.
- **Work-directory watchdog:** 2 GiB is structural.
- **Measured since (no longer hypotheses):** `ps -o comm=` shows the unresolved exec path `<VENV>/bin/python` on macOS 27.2 and is rewritable through the args (round-3 reviewer); the kernel executable path (`proc_pidpath`) of the same process is the resolved uv CPython (spikes/ingest-sysctl); the profile edits refuse every cross-process channel tried, and the converter tests pass under them (spikes/ingest-sysctl).
- **Throughput under the amended profile — a gate, not a guess:** before the product `converter.sb` changes, NFR-INGEST-1's [local] full pilot run is repeated under the amended profile and must record at least 10 pages/min (ADR-0021's bound) and the child's peak RSS (the earlier run: 65.5 pages/min, 4,025 MiB). The 20-page sample alone is recorded too: SRV-INGEST's VEC-INGEST-3 test (conversion plus the expectation checks) took 111.6 s under the product profile and 123.1 s under the amended one, one back-to-back run each on 2026-11-23; the 10 % difference is within a single run's unknown spread, so the full-run gate decides.
