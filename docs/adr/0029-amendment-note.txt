> Amendment (owner, <date>), from SRV-INGEST revision 2 review rounds 4–6 and spikes/ingest-sysctl:
> - **The inode channel is open under every profile tried.** `fsgetpath()` on a directory's inode returns its path, and `chdir` into a known path is allowed. Neither is stopped by denying `file-read-metadata` below the work root (measured, 2026-11-23); the mechanism is not identified. A confined child that scans the inode numbers near its own work directory finds a sibling run's.
> - **Decision 3's edits close the process channels only:** another process's arguments and environment (`kern.procargs2`, `kern.procargs`), its entry in the process table (`kern.proc.pid`, `kern.proc.all`), its cwd and executable path (`proc_pidinfo`, `proc_pidpath`) and the process list (`proc_listallpids`). They do not close the inode channel.
> - **The control is one converter run on the host at a time.** Every converter run, the CLI's (`reader-ingest <material>`) and the watcher's alike, holds `<data_dir>/ingest/locks/convert.lock` from just before its run until its cleanup has ended; an idle watcher waits without it. So no run exists alongside another for a child to join. The CLI answers `busy` (exit 3) while an upload converts, and an upload queued during a CLI run waits, shown as `queued` with "a command-line conversion is running". Whoever takes the lock next kills each leftover run's verified child and removes its work directory.
> - **Residual: cross-run denial of service.** A child that escaped an earlier run (it called `setsid()`, left its work directory and rewrote its arguments, so it was neither counted nor killed) survives, still confined: no network, no sockets, no information about other processes, no writes outside a deleted directory. It can find each later run's work directory, join that run's accounting and push it over its 8 GiB memory limit, failing every later conversion until the Mac restarts (whether logging out also ends it is not measured). There is no reliable signal, because the same argument rewrite hides it from the stray count; the symptom is repeated `memory_limit` failures on files that converted before, and the Import page names it with the remedy: restart your Mac. A `sandbox_check(pid)` spike may later give a signal.
> - **Sentences this amendment replaces:**
>   - Decision 2, "Convert": "For non-malicious runs, work directories are random and unique, so a concurrent run (another upload, or a CLI `reader-ingest`) is never counted or killed." and "An exploited child cannot learn another run's work directory through any channel tried (Decision 3); if a path leaked otherwise, it could join that run and push it over its memory limit, a denial of service of one conversion." are replaced by the control and the residual above: with one run at a time there is no concurrent run to count or kill, and the inode channel lets an escaped child find later runs.
>   - Threat row 1 (Malicious PDF): "no information about other processes (their arguments, environment, cwd and paths: the inbound channel Decision 3 closes)" now means other *processes'* paths only (their executable and cwd); directory paths remain learnable through the inode channel.
>   - Threat row 3 (Escape from the session): "Decision 3 keeps a child from learning another run's WORK; the [host] test replays the round-3 attack and requires that its child is not a member of the other run" is replaced by: Decision 3 keeps a child from learning about other processes; one converter run at a time (`convert.lock`) leaves no concurrent run to join; the [host] test replays the round-3 attack, requires that every process channel is refused, and records `fsgetpath` as open.
